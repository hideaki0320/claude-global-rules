# /ship パイプライン

ユーザーの指示を受けて、実装からデプロイ・品質確認まで一気通貫で実行する。

## パイプラインの流れ

### Phase 1: 実装（Claude Code 本体が担当）
1. ユーザーの指示内容を分析
2. 必要なファイルを Read / Grep で確認
3. feature ブランチで実装（既に feature ブランチにいればそのまま）
4. 実装完了

### Phase 2: Push 前チェック（並列実行）
5. **ロビン（robin-schema-guard）を起動**:
   - Supabase プロジェクトの ref を渡す
   - DB スキーマとコードの整合性を検証
6. **チョッパー（chopper-security）を起動**:
   - プロジェクトルートを渡す
   - セキュリティチェックを実行

→ ロビン・チョッパーは Agent ツールで**並列起動**する
→ 致命的な問題があれば修正してから次へ（最大2回リトライ）
→ 問題なければ Phase 3 へ

### Phase 3: Commit & Push
7. git add → git commit → git push（CLAUDE.md ルール: 確認なしで一連実行）
8. push 失敗時はエラー報告

### Phase 4: デプロイ待ち
9. Railway プロジェクトがある場合:
   - `railway status` または Railway API でデプロイ状態を確認
   - デプロイ完了までポーリング（30秒間隔、最大10分）
10. Railway プロジェクトがない場合:
    - localhost で確認（npm run dev が起動中であること）

### Phase 5: デプロイ後チェック（並列実行）
11. **サンジ（sanji-ui-checker）を起動**:
    - デプロイ先 URL（または localhost）を渡す
    - 確認すべき画面遷移を指示
    - スクリーンショットを取得
12. **ブルック（brook-performance）を起動**:
    - 同じ URL を渡す
    - パフォーマンス計測

→ サンジ・ブルックは Agent ツールで**並列起動**する

### Phase 6: 結果判定
13. 致命的・重要な問題がある場合:
    - 自動修正を試みる
    - Phase 2 に戻る（最大2回リトライ）
14. 問題なし or 軽微のみ:
    - ユーザーに完了報告

## 完了報告フォーマット

```
## /ship 完了報告

### 実装内容
- （変更ファイル一覧）

### Push 前チェック
- ロビン（スキーマ）: ✓ / ✗（詳細）
- チョッパー（セキュリティ）: ✓ / ✗（詳細）

### デプロイ
- ブランチ: feature/xxx
- コミット: abc1234
- デプロイ先: https://xxx.up.railway.app

### デプロイ後チェック
- サンジ（UI）: ✓ / ✗（詳細）
- ブルック（パフォーマンス）: ✓ / ✗（詳細）

### リトライ回数: 0回
```

## 特殊ケース

### Supabase プロジェクト ref の取得
- プロジェクトの .env.local または .env から NEXT_PUBLIC_SUPABASE_URL を読む
- URL からプロジェクト ref を抽出（https://<ref>.supabase.co）
- .env がなければロビンをスキップ（警告のみ）

### Railway がない場合
- Phase 4 をスキップ
- Phase 5 は localhost:3000 で実行

### koso-navi プロジェクトの場合
- Phase 2 で追加: **ナミ（nami-subsidy-validator）** を起動（助成金ロジックに関わる変更の場合のみ）

## 守るべきルール
- main ブランチに直接コミットしない
- リトライは最大2回。それ以上はユーザーに報告して判断を仰ぐ
- 各エージェントの結果を握りつぶさない。全て報告に含める
